## 独立结论

主要用户路径已有明确实现和自动回归，但产品状态语义仍有可定位的问题：宏把提交完成称为执行完成；多行 CMD 粘贴可能先提交前缀、再丢弃超长尾部；后台会话错误不能在切回时恢复；电源“全部断开”的异步结束链没有把掉电确认失败保留在主界面。建议在发布承诺上区分“已有功能”“受控测试通过”“现场已验收”。当前证据不能支持 Win7 实机、真实 SFTP/串口/IT6332A、125/150/200% DPI 或 8 小时稳定性已经通过。

## 问题清单

### P-01 宏“执行完成”实际只证明最后一步已入队；“停止”仅停止后续提交

- 严重度/状态：P2，源码确定；尚未执行针对性真实窗口复现。
- 位置：MainWindow.cpp:3617–3624、3777–3806、3814–3826；SessionService.cpp:108–113；QueuedConnection.cpp:36–70。
- 事实：SessionService 返回 `state=queued, execution=unknown`。SendNextCommandStep 只检查 SendBytesToActive 的 bool，在最后一步入队后立即清除运行状态并显示“执行完成”。StopCommandSequence 仅 KillTimer/清运行字段，没有撤销已经入队或设备正在执行的动作。
- 触发/复现：CMD 保存两步宏，第一步 `ping -n 11 127.0.0.1 >nul`，第二步 `echo MACRO_DONE`，短间隔执行；观察最终输出前是否已显示完成。另设 5 秒间隔，在第一步运行期间点 Stop，观察第一步仍继续。串口使用带 ACK 的替身区分发送/设备完成。
- 预期：标记“已提交 2/2；执行结果请查看输出”；Stop 标记“已停止后续提交；已提交内容可能继续执行”。除非获得协议定义的执行 ACK，不显示业务完成。
- 实际依据：以上确定代码路径；此处没有虚构截图。
- 影响：依赖宏控制设备/等待 CMD 任务的操作者可能过早开展下一步，或者误认为停止已中断设备。
- 修复/验收：保留现有进度环与卡片布局，修正文案和状态枚举；加入慢执行与 Stop 后继续输出的 GUI 断言，不能仅检查按钮复位。若未来加入任务完成协议，应单独定义关联 ID 与设备 ACK，不能把完整批次 FIFO 称为任务互斥。

### P-02 多行 CMD 粘贴先提交前缀，再验证尾行，失败后尾行与原草稿无法恢复

- 严重度/状态：P2，已在提取的生产分支＋生产编辑器模型运行确认；真实 GUI 针对性复现未运行。
- 位置：MainWindow.cpp:4249–4262；terminal/CmdLineEditor.h:18–23、82–103。
- 触发：已有草稿 `echo PRESERVE `，粘贴 `SAFE\r\n` 加 8192 个 `x`。完整第一行很短，满足网络/提交限制；末尾未完成草稿超过 8191 字符。
- 预期：先验证完整粘贴方案；拒绝时保留原草稿、剪贴板和光标，并且不发送任何前缀；或明确让用户选择部分提交并把未提交部分保存在可恢复草稿。
- 实际：分支先 SendBytesToActive；成功后 SubmittedBatch 清空 editor；尾行 Insert 返回 false，仅显示“CMD 尾行过长”。日志显示 accepted_batches=1、draft_before_chars=14、draft_after_chars=0、errors=1。
- 影响：复制多段调试命令/长参数的工程师既丢失当前编辑状态，又可能因重试整个粘贴而重复执行已经提交的前缀。
- 修复：在临时编辑器或字符串上完成尾行长度、编码、整体批次等全部验证，再提交；只有提交成功才原子更新 editor。不要自动重发。
- 回归：尾部 8190/8191/8192 字符；中间插入；CR/LF/CRLF；前缀拒绝；编码不可表示；失败后原草稿和光标保持；任何拒绝前 TX=0。
- 证据：上述独立 probe 三个文件。替身仅代替发送接受与 Win32 绘制，不代替实际 cmd.exe 执行。

### P-03 “全部断开”没有闭合电源掉电失败的用户反馈

- 严重度/状态：P1 候选，需要 Windows 受控故障和硬件两阶段确认。已确认的是状态/反馈代码链缺口，不声称实际设备未掉电。
- 位置：MainWindow.cpp:3544–3559、1742–1751；PowerService.cpp:653–697、789–790、863、889–892；PowerPane.cpp:458–474。
- 事实：MainWindow 直接 Submit disconnect，仅保留 bool pending，不保存 action ID，也不把动作交给 PowerPane pendingActions。PowerService::Disconnect 捕获 StopTask 掉电异常后记录 state.error，继续清连接；Execute 随后将 disconnect action 标 completed。主窗发现 connected=false 即隐藏电源页/移除条目，没有读取 error 或发出完成/失败提示。之前“掉电确认处理中”的非错误状态 3.5 秒自动消失（MainWindow.cpp:4045–4046）。
- 用户风险：用户看到连接清空，却缺少“输出状态未知，必须人工核实”的持续提示；操作记录可能只显示 disconnect/completed。不能由此推断软件把实际通道状态写成 OFF：源码将它们置 null，这点是正确的。
- 复现：在受控 SCPI 端启动 CH1 定时任务后，对 OFF 或 OUTP? 读回制造超时；点“全部断开”，记录 action、power.get/state、主窗口状态、截图和设备通道。真实 IT6332A 再执行拔线场景。
- 预期：连接可以断开，但主窗保留失败/未知摘要及受影响通道；记录“连接已断开，CH1 掉电未确认”，不能只写 completed。非任务通道不应被关闭。
- 修复：保存 disconnect action ID；区分 transportDisconnected 与 taskOutputsConfirmed；等待最终结果后在主窗保留错误。不要增加网络断连权限。
- 验收：成功与失败分别截图；失败不隐藏唯一告警；重开电源页可查记录；停止/退出仅尝试关闭 ownedChannels，未拥有通道保持。

### P-04 后台会话错误只进日志，切回后没有恢复错误原因

- 严重度/状态：P2，源码确定；动态重绘延迟为候选。
- 位置：MainWindow.cpp:2046–2055、3567–3605；MainWindow.h:82–114。
- 事实：MessageStatus 对非 activeSession 只 WriteStatus，不保存 lastError；SessionState 没有对应错误字段；SwitchSession 只切指针/终端状态，不恢复该会话最后错误。连接卡只显示通用“已断开”（MainWindow.cpp:2766），不呈现原因。
- 复现：打开 A、B；保持 B 激活，让 A 发生端口断开/网络拒绝；切到 A。检查是否只能见断开而无法在 UI 得知原因；打开日志作为对照。
- 预期：在现有连接卡提供轻量错误状态或提示，切回显示该会话最近错误；保持活动会话日志归属，错误持久到被替代/确认。
- 影响：同时监视多串口的测试人员容易错过后台失败，排障需自己寻找日志。
- 修复/验收：每 SessionState 保存 lastStatus/lastError，并在状态事件时失效对应卡片；32 会话下验证 A/B 状态不串用。没有真实截图前不把“颜色永远不刷新”列为已确认。

### P-05 串口卡片仍以“TCP”提示，和已移除原始 TCP 的操作入口不一致

- 严重度/状态：P3，源码确定。
- 位置：MainWindow.cpp:2772–2774；对照连接成功提示 MainWindow.cpp:3458–3462。
- 事实：成功提示写 WebSocket，卡片写 `TCP 7000 · 共享`。WebSocket 确实运行于 TCP，但产品提示会使历史用户再次尝试原始 TCP/Telnet；这并非“旧业务仍存在”的证据。
- 建议/验收：采用“WebSocket 7000 · 共享”，原始 TCP 拒绝提示注明升级方法。双主题下验证不截断并检查中文/端口可辨。
