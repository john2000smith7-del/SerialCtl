## 串口交互卡顿的已确认代码路径

1. SerialDevice 原先使用同步文件句柄。等待串口 ReadFile 与交互 WriteFile 共用同一同步文件对象，存在读写串行等待。现改用 FILE_FLAG_OVERLAPPED，读写分别持有操作事件，共用持续取消事件。关闭先取消、等待操作完成再释放句柄。保留第一字节返回模式：空闲读取的 1000ms 超时不是强制收包等待。
2. 原 PostData 在投递本地显示前调用网关 Publish；该调用持网关全局锁进行历史序列化和订阅客户端分发。本地显示现在先交接给窗口，再发布网络事件，且不再通过 SessionService JSON 状态查询取得每批代码页。
3. 原接收积压续批依赖 10ms WM_TIMER；Windows 常规计时粒度还会影响 6ms/GetTickCount64 预算的准确性。可见窗口现在使用 steady_clock 的 2ms 工作预算、处理后立即 UpdateWindow 终端，并在正常绘制机会继续积压，不引入接收刷新定时等待。最小化/不可见时保留原后台定时调度。
4. 活动终端在接收积压下获得三次优先机会，第四次处理原始队首，计数跨批保留。保持每个会话内输入/输出顺序，避免其他会话的大输出埋住当前串口回显，同时保证后台会话继续前进。
5. 共享串口逐字节帧头读取原先反复创建事件并调用 WSARecv；现用每 Stream 一个接收事件、16KiB 预读及偏移游标。缓冲、同步读取、重叠读取和 Ping/分片均检查完整消息期限。
6. 原 SSH IsConnected 与阻塞 WriteFile 共用 writeMutex，界面查询连接状态也会等待。现状态为原子快照，读写为可取消重叠管道；停止不再依赖 Sleep 重试拿锁。

没有取消硬件发送工作线程及必要的完整批次同步。直接在 UI 线程等待硬件 WriteFile，在 CTS 流控或驱动异常时会重新引入卡顿。没有添加多客户端写入租约或额外授权步骤。

以上是源码级等待风险及其整改，不能直接推断用户现场每一毫秒都来自同一原因。实体 UART、USB 驱动和物理屏幕延迟仍需现场测量。
