## 卡顿原因及整改

1. 同步串口句柄的读写可能相互等待。SerialDevice 使用独立的重叠读写操作和可取消事件，停止时先取消并回收操作，再释放句柄。空闲读的 1000ms 超时是等待第一字节的上限，不是对每批数据添加 1000ms 延时。
2. 原本地接收先执行网关同步发布，可能等待网络历史和订阅者的全局锁。现在先交接本地接收，网关发布、会话注册及资源移除按顺序交给独立工作线程；溢出显式标记历史缺口，避免无提示地伪装完整历史。
3. 原可见终端积压依赖 10ms 计时器；现在每次按 steady_clock 的 2ms 预算处理并立即更新终端，剩余数据通过下一次正常绘制机会继续。活动会话优先，同时保持会话内部顺序和后台会话进度。
4. 连接完成、全部断开和窗口关闭曾等待工作线程。现在通过取消信号、拥有所有权的后台回收和完成通知保持窗口消息循环；连接启动与取消竞态也由后台负责停止实际 transport。
5. 远程自动发现原先对每个候选端口重复解析，解析耗时不在连接预算中。现在一次解析后并行探测原有端口，数字 IP 走直接路径；域名查询使用同一程序的受限子进程，以便 Windows 7 上取消和回收。IPv4/IPv6 候选和 WebSocket 建立共享单调截止时间。Windows 7 不支持 GetAddrInfoEx 异步参数，依据 [Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/api/ws2tcpip/nf-ws2tcpip-getaddrinfoexw)。
6. SSH 查询连接状态原先可能等待写锁；现用原子状态及可取消重叠管道。终端历史/预览共享不可变快照，持久绘制缓冲按尺寸/DPI 回收。

这些是代码中可验证的等待路径，不代表已经测出某现场设备卡顿的唯一原因。保留确保设备批次有序所需的同步与工作线程。

## 模块与所有权

- TerminalViewport 持有绘制、GDI 缓冲、选区、滚动、命中与视口状态；TerminalViewportController 负责网格和输入预览策略。主窗口仍负责窗口装配与消息适配。
- CommandMacroController 持有命令模型、文件导入导出、运行状态与绑定会话/编码的发送计划。原文件格式与用户提示保留。
- AiDeviceBridge 持有设备观察、Boot 中断与命令/恢复策略；主窗口只组合上下文、执行 UI 回调。未引入自动重复发送或新的电源操作。
- SftpController 持有队列、传输状态、取消和两个工作线程；UI 回调可以注销，结果留在控制器管理，窗口销毁前回收工作线程。
- 本地输入仍需有序的发送交接；安全设备环境不会让串口驱动、系统调度和物理链路变为零耗时。
