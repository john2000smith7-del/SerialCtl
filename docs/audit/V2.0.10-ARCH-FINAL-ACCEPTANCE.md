## 交互卡顿路径

1. 原同步串口读写可能互相等待。`SerialDevice` 改用独立的重叠读写和可取消事件，停止时先取消并回收操作。空闲读的 1000ms 是等待第一字节的上限，不是每批数据固定延迟。
2. 原本地接收先同步向网关发布，网络历史和订阅者的锁可能阻塞收显。现在先交接本地接收，网关输出及会话注册在独立线程中按序发布；有界队列溢出会明确标记历史缺口并中断受影响订阅，不能静默伪装完整历史。
3. 原可见终端积压依赖 10ms 计时器。现在用单调时钟分片处理并立即更新终端，余量经正常绘制机会继续；活动会话优先，同时保持会话内顺序及后台进度。
4. 原连接完成、全部断开和关闭窗口可能等待线程或网络服务。现在取消及资源回收由有所有权的工作线程处理，UI 仅在工作完成后回收句柄；关闭期间继续处理窗口消息。
5. 原远程自动发现对多个端口重复解析，DNS 不计入连接超时。现在数字 IP 直接走数值解析，名称解析采用可取消的同程序子进程，一次解析后并行探测端口，IPv4/IPv6 连接和握手共享截止时间。[Windows 7 的 GetAddrInfoEx 异步支持限制](https://learn.microsoft.com/en-us/windows/win32/api/ws2tcpip/nf-ws2tcpip-getaddrinfoexw)决定不能直接依赖较新异步接口。
6. SSH 连接状态不再等待写锁，进程管道可取消；终端预览共享不可变历史，窗口和终端复用绘图资源。
7. 手动桌面测试发现持续输出时的快速侧栏点击未在 60ms 内响应；原 UI 线程每次操作同步写入 25 个配置项。`1d58cdc` 将完整设置快照交给后台合并写入，正常关闭时等待最后快照持久化。原失败记录只能证明点击命中且状态未及时变化，不能单独证明磁盘是唯一原因；匹配的 Windows 和桌面复测是验收条件。
8. 复查发现终端视口拆分时遗漏了基线对窗口拖动、侧栏拖动和动画期间重排的保护；这会让每一帧都重新计算各会话的终端尺寸。`e7218ab` 恢复原有延后规则，在操作结束时提交最终尺寸，并新增三个场景的回归断言。`23277a8` 的 Windows 构建、5 次交互重复和配对性能测试均通过这些断言。

上述是经源码和受控测试确认的等待路径，并不证明现场只有一个卡顿原因。设备命令顺序和必要的生命周期同步仍被保留。物理串口、USB 驱动、操作系统调度和显示器扫描不能保证绝对 0ms。
