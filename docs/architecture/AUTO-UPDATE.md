# 双文件自动更新（V2.0.0）

## 交付与行为

每次正式发布必须交付精确配套的完整 ZIP 和内嵌签名 `update.json` 两个下载文件。服务器保留现有静态目录和 `[update] url=` 配置方式，用户不运行签名工具，也不维护外置 `.sig` / `files`。每次启动后台检查，可信新版先提示，用户确认后下载并在原有空闲条件下安装重启；忙碌和已发生用户操作时不突然重启。

V1.10.0 及以前不能读取新格式，需要手动部署一次支持双文件的客户端。新客户端仍可验证旧 schema 1 外置签名 feed，以保留兼容性；正式新交付只使用双文件格式。

## 签名封装

外层 JSON 精确三个键：`schema: 2`、`payload` 字符串、`signature` 字符串。`signature` 是 RSA-2048 / PKCS#1 v1.5 / SHA-256 的 256 字节签名，以 512 个小写十六进制字符表示，签署的是 `payload` 解码后字符串的原始 UTF-8 字节。无须跨语言 JSON 规范化，外层空白不会改变签名；任何 payload 字节变化都会导致失败。

客户端先用有限深度、拒绝重复键的解析器读取封装，再验签，验签后才解释 payload。payload 精确包含 schema 2、product SerialCtl、architecture x64、canonical Vx.y.z、files 数组和 archive 对象。archive 包含同源相对 ZIP URL、大小和 SHA-256；files 中每个批准的扁平运行文件包含名称、大小、SHA-256 和兼容旧文件记录的 url 字段（ZIP 模式不请求该字段）。内嵌签名不能包裹旧 schema 1 来绕过 ZIP 元数据要求。

元数据上限 64 KiB、嵌套深度 8；ZIP 上限 512 MiB、ZIP32 条目至多 4096、中央目录至多 8 MiB；每个提取运行文件上限 32 MiB、运行文件总量 64 MiB、至多 32 文件。ZIP64、多卷、加密、重复路径、符号链接、危险路径或未知压缩方式不支持。支持 stored 和 DEFLATE，使用静态、仅解压的 miniz tinfl 3.0.2，不依赖系统 Shell、PowerShell、.NET 或外部 DLL。

URL 不允许跨源、凭据、重定向、歧义转义、查询串或片段；沿用 WinHTTP 超时与取消隔离。元数据 15 秒预算，ZIP 下载预算 10 分钟。下载按块写入随机隔离暂存文件，不把整个 ZIP 保存在内存。下载完成先验证全 ZIP 长度/摘要，再解析目录；只解压签名清单中的现有白名单根文件，验证本地/中央头、大小、CRC、解压界限和每文件 SHA-256。其他成员（包括 drivers、update.ini）不写入安装暂存目录。

临时 ZIP 在验证提取后删除。staging 保留已签名 update.json 和 files 子目录（仅客户端内部使用）。安装器重新验签、验证每个暂存文件和 VERSION，复用既有事务备份、实例排斥、健康握手及失败恢复，不需要在 GUI 主线程重新散列整个驱动包。

## 发布端

`tools/new_update_feed.py --archive <已验证完整ZIP> --output-dir <新目录> --private-key <离线密钥>` 用于发布方生成配套文件。输出目录只有原 ZIP 和 update.json；ZIP 原字节不修改，工具核对正式包标识、测试标记及运行文件摘要，检查私钥与客户端内置公钥一致，签后复验。该命令由发布方执行，用户只上传结果。

签名私钥离线保管，不能提交 Git、随包、放进网站或默认上传 CI。Windows 正式构建在验证整个包之后，通过 `--describe-archive` 输出公开候选 payload，供受控离线签名；候选 payload 尚未签名，不能作为用户部署文件。发布工作流只接收公开的、已签名 update.json 的 Base64，下载指定成功 main 构建产物，复核 ZIP SHA-256，再以 `--verify-archive --metadata` 验证内嵌签名与该 ZIP 的描述完全一致，通过后只上传 ZIP 和 update.json 两个资产。签名能力不可用时禁止生成伪签名或不完整正式发布。

V2.0.0 身份的公钥 SPKI SHA-256 为 `196b703ac1274da483936513794f0c03eb7be806c302db4d932b30378a78a21a`。2026-10-25 曾因另一个工作环境中未找到原私钥而发布新身份 `1b54f808072ac93c97d98d007a8e8c71d41a17834a0c5d810c614e9d75a05ae7`。2026-10-26 原私钥在原工作环境恢复，经用户授权 V2.0.4-r1 重新使用原身份；V2.0.2 原客户端可直接升级。活动身份记录为 `release-signing/identity.json`，原私钥路径及权限见 AGENTS.md；它没有加密仓库备份。新身份的公开记录保留在 `replacement-v2.0.4.json`，其密文文件和拥有者原恢复口令仍只属于该历史身份。恢复工具默认只选择匹配活动身份的备份，没有活动备份时明确拒绝，不自动尝试历史钥匙；显式恢复也需匹配当前公钥并拒绝覆盖。明文私钥、口令及拥有者的私密恢复 ZIP 不提交、不上传 CI、网站或应用发布包。已安装新公钥 V2.0.4 的用户需另行迁移，恢复原身份不等于这些已安装客户端获得双钥匙信任。

正式 Windows 构建、CTest、PE/Win7 导入检查、包白名单和 ZIP 重开是发布门槛。Python 回归覆盖双文件签名与 ZIP 描述匹配；受控 WinHTTP/文件测试覆盖新旧协议。正式完整 ZIP 还通过一次临时测试密钥签名到原生解析/提取的回归；临时测试密钥不出测试目录，不用于正式签名，不执行归档程序或替代真实内网升级验收。

## 部署和恢复

先上传版本化 ZIP，再切换 update.json。网站只需静态 GET，允许 json/zip MIME，不需要执行权限或 Python。只保留两个活动部署文件时，在新 JSON 生效后移走旧 ZIP；旧客户端读取缓存清单导致旧文件不可达时会保留当前版本，下次启动重新检查。建议 JSON 禁用缓存，版本化 ZIP 可缓存。

配置、命令、日志、驱动和未批准的用户文件不替换。恢复行为及日志位置见 [用户说明](../package/AUTO-UPDATE.md)。签名提供来源/完整性，不提供更新可用性、密钥轮换或撤销；换 URL 不更换信任根。真实 Win7 SP1/10/11、TLS/内网站点、设备、磁盘满、断电及安全软件干预仍需现场验证，不能从构建或离线测试推断通过。

## V2.0.3 确认后下载

启动先读取清单并验签、比较版本；可信更高版本通过检查后显示强制提示，仅“确定”。点击确定前不请求压缩包、不创建下载暂存目录；关闭提示退出程序。确认后显示真实字节下载进度与校验阶段，完成后沿用安全空闲安装／重启。下载或安装失败时重试或退出，不能绕过已要求的更新继续操作旧版。网络不可用或清单不可信时不能伪称发现新版，沿用离线可用行为；已经运行的设备任务不突然中断，空闲重启确认升级。

服务器依旧只上传版本ZIP和其内嵌签名update.json，update.ini不变。已安装V2.0.2首次升级到V2.0.3使用旧客户端原有行为；升级完成才采用新增提示。
